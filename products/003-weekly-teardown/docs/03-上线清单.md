## 一、上线前的人工动作

这些我不代跑（部署类动作一律人工门）。全部在 `nanisle-product/products/003-weekly-teardown/` 目录下执行。

### 1. AWS 侧（只有一件事）

建一个最小权限 IAM 用户，只给 `ses:SendEmail`。

**不需要新建任何 AWS 资源，不需要 `cdk deploy`**——`nanisle.com` 的域名身份在 001 的 SES 账号里已经验证过，同账号直接可用。

> SES 沙箱在 2026-08-24 已确认解除（5 万封/日），收件人不需要逐个验证。

### 2. D1 迁移（**只有这一次是可逆的**）

```bash
wrangler d1 migrations apply nanisle-weekly-teardown --remote
```

⚠️ **这一步之后 `migrations/0001_init.sql` 就冻结了。** 本轮开发期间它被改过六次（加 `stopped`/`claimed_total`/`route_count`、加 `reason_kind`、`report` 加 `dossier_rev`、加 `weekly_email`/`email_optout`，**上线前终审加 `weekly_change`/`scan_appeal`/`candidate_open` 三张表 + `scan_candidate.topics`/`scan_exclusion.pushed_at` 两列 + `ix_quota_day`,并把 `ix_report_recent` 换成 `ix_report_latest`**，**冻结前最后一轮再加 `week_view` 一张表 + `ix_week_view_at`**），每次都是直接改 0001 而不是叠 0002——因为这个库从未 `--remote`。**首次 `--remote` 之后这条路作废**，以后任何 schema 改动只能新增 `0002_*.sql`。

终审那一批的三张表都是「列 0002 能加、**历史不能**」的东西(决策 8 的三个信号 + 跨周结论),所以它们必须在**第一次 `--remote` 就位**——晚一周上线,就少一周历史。`week_view` 是同一条逻辑的第四张:第二个月复盘要数的是「这两个月里翻过几次」,而历史只能从落库那天开始攒。

**冻结前对一遍:0001 现在是 21 条 `CREATE` —— 14 张表 + 7 条索引**(6 条普通索引 + `ux_scan` 那条 UNIQUE)。`--local` 跑完 wrangler 报「22 commands executed successfully」,多出来的那一条是它自己往迁移表里记的一笔。

| 表 | 存什么 | 谁在读 |
|---|---|---|
| `dossier` | 用户那份可见可改的关注定义 | 全站 |
| `weekly_scan` | 一周一行的台账(四个数 + `stopped` + `route_count`/`claimed_total`) | 第一屏、翻周列、cron |
| `scan_candidate` | 进清单的仓(含 `topics`) | 第一屏、跨周 diff |
| `scan_exclusion` | 被筛掉的仓 + 理由(含 `reason_kind`/`reason_source`/`appealed_at`/`pushed_at`) | 第一屏的排除清单 |
| `report` | 深度报告(payload 整份 JSON) | 报告屏 |
| `inflight` | 在跑的那一单(刷新不丢进度) | 报告屏 |
| `quota` | 每日次数配额 | 两道闸 |
| `daily_spend` | 全局花费闸 | 报告端点 |
| `weekly_email` | 门铃发信台账(主键即幂等) | cron |
| `email_optout` | 退订名单 | cron / `/unsub` |
| `weekly_change` | 一周一行的跨周结论(计数列 + 整份 `WeekDiff`) | 跨周屏、邮件 |
| `scan_appeal` | 申诉的永久台账(只增不改) | 重跑恢复、决策 8 |
| `candidate_open` | 深度报告的点击台账 | **风险 2 的判据** |
| `week_view` | 翻阅台账(哪一周、哪条端点、那一刻最新的是哪一周) | **风险 4 的判据**,不上页面 |

七条索引:`ux_scan`(周扫幂等)、`ix_report_latest`、`ix_report_commit`、`ix_quota_day`、`ix_change_recent`、`ix_appeal_repo`、`ix_week_view_at`。要机器核一遍就跑:

```bash
wrangler d1 execute nanisle-weekly-teardown --local   --command="SELECT type, name FROM sqlite_master WHERE name NOT LIKE 'sqlite_%' AND name NOT LIKE 'd1_%' AND name <> '_cf_METADATA' ORDER BY type, name"
```

### 3. Secrets

```bash
wrangler secret put NANISLE_SSO_SECRET     # 必须与主站同值，否则手递票验不过
wrangler secret put ACCESS_CODE            # 站长凭证，走 x-access-code 头；支持逗号分隔多码
wrangler secret put DEEPSEEK_API_KEY       # 不配自动落回 mock（不报错）
wrangler secret put GITHUB_PAT             # 强烈建议，见下
wrangler secret put EMAIL_UNSUB_SECRET     # 不配 = 不发邮件，其余功能完整
wrangler secret put AWS_ACCESS_KEY_ID
wrangler secret put AWS_SECRET_ACCESS_KEY
```

**`GITHUB_PAT` 为什么是强烈建议而不是可选**：阶段 4 实测，匿名档 search 是 10 次/分钟，8 条检索词 × 2 路 = 16 次要等 **112 秒**，而交互路径的 `SCAN_BUDGET_MS` 默认 75 秒（受 CF 那条「100 秒无字节即 524」的线约束，提不上去）。结果是**每个用户手动触发周扫都会拿到一份残缺清单**（`queryCount: 7/8` + 一句 `stopped`）。配了 PAT 之后 search 是 30 次/分钟，这个问题消失。

产品是诚实的（残缺会在页面和邮件上明说），但不配 PAT 等于让每个人都撞上这条诚实声明。

### 4. 部署

```bash
npm run deploy                      # 产品，必须先
cd ../../../web && npm run deploy   # 主站，必须后
```

**顺序不能反的原因**：`web/wrangler.jsonc` 的 `services` 数组里已经有 `{ binding: "WEEKLY_TEARDOWN", service: "nanisle-003-weekly-teardown" }`，而那个 Worker 现在还不存在。Cloudflare 在部署时会校验 Service Binding 的目标，指向不存在的 Worker 会直接失败。

## 二、上线后的验证（**按风险排序，不是按功能排序**）

前两条是**刹车**：不过就要停下来改方案，不是改代码。后面几条是常规验收。

### 验证 1 · 能进得去（30 秒）

```bash
curl -s https://nanisle.com/products/weekly-teardown/api/health | jq
```

期望：`{ ok: true, provider: "deepseek", hasPat: true, hasDb: true, db: "ok" }`

`db` 这个字段是**上线前终审加的**,而且它就是为这一步加的:原来 `hasDb` 只是
`Boolean(env.TEARDOWN_DB)`,**上一行那条 `migrations apply --remote` 忘了跑的话它照样回
`true`**,然后每一个真端点 500 —— 一个只在什么都没坏时才说真话的健康检查。现在它真的跑
一次 `SELECT 1 FROM dossier LIMIT 1`,四种结局各有各的处置:

| `db` | 意思 | 该做什么 |
|---|---|---|
| `ok` | 库接上了,表也在(空库也算 ok) | 往下走 |
| `no-tables` | binding 在,表不在 | **回到上一步跑 `migrations apply --remote`** |
| `no-binding` | `env.TEARDOWN_DB` 根本不在 | 查 `wrangler.jsonc` 的 `d1_databases` |
| `error` | 别的错(D1 这会儿不通) | 看 Worker 日志,只能等 |

`provider: "mock"` = `DEEPSEEK_API_KEY` 没配上（代码是有意落回 mock 不报错的，所以只能从这里看出来）。

然后浏览器打开 `https://nanisle.com/products/weekly-teardown`，走一次登录，确认 SSO 手递之后落到 `/products/weekly-teardown/app` 而不是 302 回介绍页死循环（002 在 2026-08-26 踩过这个，`landing` 留空就会）。

### 验证 2 · SSE 心跳能不能穿过 Service Binding ⚠️ **最高优先级**

**这是整个项目唯一无解的未知**（[`02-技术方案.md`](02-技术方案.md) 的技术风险 3）。

**为什么本地验不了**：本地 `next dev` 走的是反向代理，线上走的是 Service Binding，两条路完全不同。003 自己这一跳的 SSE 已经在真 workerd 上验过（阶段 7 实跑记录里有心跳时间戳），但**浏览器 → 主站 Worker → Service Binding → 003** 这条链上，心跳会不会被某一跳缓冲住，只有线上知道。

代码里加了 `x-accel-buffering: no`，那对某些代理有效，**对 Cloudflare 不保证**——它不构成验证。

**怎么验**：

1. 登录后进第一屏，跑一次周扫拿到候选清单
2. 点某一行的「拆开看看」
3. **打开浏览器 DevTools 的 Network 面板，盯那条 `POST /api/report` 的响应流**

**通过判据**：从请求发出到第一个 `result` 事件之间，**每 10 秒能看到一个 `data: {"type":"ping"}` 到达**，并且整个请求在 60–120 秒后正常出报告，**不是 524**。

**不过怎么办**（心跳没到达 / 请求 524）：

| 现象 | 含义 | 下一步 |
|---|---|---|
| 事件全部在最后一次性到达 | 某一跳做了缓冲 | 深度报告改成「提交后立即返回 202 + 前端轮询」形态。`inflight` 表和轮询接回已经建好了（阶段 7 的刷新接回就是这套），改动集中在把 SSE 那条路换成 202，估 1h |
| 100 秒左右 524 | 心跳没穿过去 | 同上 |
| 心跳到了但报告本身失败 | 不是这个问题 | 看 `wrangler tail` 的日志 |

**这一条不过不影响别的功能**：档案、周扫、第一屏、申诉、门铃邮件都不走 SSE。

### 验证 3 · 出口 spike ⚠️ **这是方案里写死的刹车**

[`02-技术方案.md`](02-技术方案.md) 的「阶段 0」原话：**「不过就改方案，不是改代码」**。它需要 Cloudflare 出口 IP 才能跑，所以一路推迟到了部署之后。

```bash
curl -s -H "x-access-code: <你配的 ACCESS_CODE>" \
  "https://nanisle.com/products/weekly-teardown/api/__spike?n=20" | jq
```

（`n` 默认 5、上限 20；每个 URL 各探 n 次，返回 `min / p50 / p95 / max` 和成功次数。整体有 60 秒墙钟预算 + 每探 10 秒超时，最坏 70 秒，进不了 524 线。）

**通过判据**（方案原文）：

- **GitHub 带 PAT 无 403**
- **HN Algolia 20/20 成功且 p95 < 2 秒**

**不过怎么办**：方案写的是**当周退回 skill 形态**。这不是临时加的托辞——「为什么不做成 Claude Code skill」那节论证过，skill 形态给不了的只有跨周状态，而如果 CF 出口根本连不通这些源，跨周状态也就无从谈起。

**一个容易误判的点**：GitHub API 强制要求 `User-Agent` 头，不带直接 403。代码里所有 GitHub 请求都带了 `User-Agent: nanisle-weekly-teardown`，所以如果这里出现 403，**是真的被限流或被封，不是忘了带头**。

### 验证 4 · 端到端跑一份真报告

用你自己的档案（那句话：「我想跟踪 AI agent 的记忆与上下文工程」）：

1. 建档案 → 四类字段都非空，`queries` 5–8 条
2. 跑周扫 → 候选 ≤5（申诉后可能更多）、排除清单有分组、台账四个数字与诚实声明一致
3. 点一个候选 → 深度报告两节

**报告出来之后重点看三样**（这是这个产品的全部卖点，也是最容易出问题的地方）：

| 看什么 | 通过判据 |
|---|---|
| **永久回链** | 随便点开节 2 的一条 takeaway 挂的链接，**看得到引文那几行**。链接里必须是 40 位 commit sha，不是 `blob/main/` |
| **锚定总账** | 页面上有「模型给了 N 条，M 条挂得上原文，K 条挂不上已丢弃」和 `anchoredRatio` 百分比。**丢掉的能展开看到** |
| **降级标注** | `notes` 区块**没有折叠开关**。中文项目在 HN 上大概率没记录，那时应该明写「这个项目在 HN 上没有记录」而不是空着 |

### 验证 5 · cron

不用等到周一。手动触发：

```bash
# 线上没有 --test-scheduled，用 Cloudflare Dashboard 的 Cron Triggers 面板手动触发，
# 或者本地: npm run build && wrangler dev --local --test-scheduled
#           curl "http://localhost:5201/cdn-cgi/handler/scheduled?cron=0+8+*+*+1"
```

> 注意：**`/__scheduled` 在这个产品上打不通**——有 `assets` 的 Worker 会被资产层按 `not_found_handling` 吞掉，返回 SPA 的 index.html。能用的是 `/cdn-cgi/handler/scheduled`。

`wrangler tail` 里应该看到 `[cron] … 起跑` / 每人一行台账 / `[cron] 收工:… 信 sent=1 …`。

**收到信之后确认三件事**：邮件里**没有报告正文**（门铃不是报纸）、有一个回网页的按钮、退订链接点了真的生效。

**还要确认一件不在信里的事**(上线前终审加的):那一趟的跨周结论**落库了**。

```bash
wrangler d1 execute nanisle-weekly-teardown --remote --command "SELECT * FROM weekly_change"
# 第一周:prev_week_of = NULL、四类计数全 0、changed = 0(如实说没有可比的上一周,不假装有增量)
curl -s https://nanisle.com/products/weekly-teardown/api/scan/changes -b "<会话 cookie>" | jq
```

这一步比信本身重要:信发失败(SES 一个 403)时**认领行不删也不重试**,那封门铃永远不会补发
——如果结论只在信里,那一周的换血就彻底没了。所以现在的顺序是**先落库再发信**,而且
**退订的人照算照落库,只是不发信**(`收工` 那行的 `optout=1` + `复查 checked=N` 一起出现
就是对的)。

## 三、已知会带上线的限制

这些都是**有意接受**的，不是遗漏。写在这里免得上线后当成 bug 查。

| 限制 | 说明 | 归宿 |
|---|---|---|
| **第一周没有增量** | 物理上没有「上一周」，邮件里会如实说「这是第一周，没有可比的上一周」 | 第二周自动消失。这是产品方案 TL;DR 承认的代价 |
| **申诉不学习** | 强制入列只影响这一周这一份清单，下周同一个仓照样被同一条规则筛掉 | 决策 8 的画像修正建议才是它的归宿（「被申诉过两次」是规则触发条件之一） |
| **中文项目在 HN 上覆盖为零** | V2EX API 未实测。报告里会明写「这个项目在 HN 上没有记录」 | v1 接受 |
| **`admitted` 可以 > 5** | 申诉的后果。邮件模板和第一屏都不截断 | 有意 |
| **两个标签页同时点「拆开看看」会跑两趟** | busy 判定是 TOCTOU。`gen=2/天` 兜住了钱，副作用是第二趟刷新后接不回进度 | 不修（修它要动 inflight 的删除口径） |
| **`/api/v1/items/<storyId>` 会拉整棵评论树** | 82 评论的帖约 35KB，两千条的超大帖会是几 MB。兜底是 10 秒超时走降级 | 记着，暂不改 |
| **cron 单趟上限 500 个档案** | 超过记 error 日志并只扫前 500 个 | 真到那天按决策 T5 **分片到多个 cron 时刻**，不是改成并发（共享桶的约束不会因为并发消失） |
| **真实容量是 20-25 人(带 PAT),不是 500** | 上面那个 500 挡的是内存,不是时间。整趟预算 13 分钟,撞上之后被记 `notReached` 的**永远是最后注册的那几个人**（`listDossiers` 按 `created_at ASC` 排,每周同一个顺序）—— 那不是「这周运气差」,是「他们每周什么都收不到」,唯一的痕迹是收工日志里一个整数 | 不动 schema:改成按「最久没扫到的排前面」(`MAX(week_of)` 从 `weekly_scan` 现算),饿死变轮流。**当前用户数下不咬人,所以留到上线后**(docs/02「上线后再说」) |
| **重跑保留申诉,但不是每一条都保得住** | 重跑会从 `scan_appeal` 把这一周的申诉搬回来,**除非这一趟根本没搜到那个仓**(排名掉出 1000 条上限 / 检索词改过 / 提前收工)。硬搬会让台账等式说谎 | 不搬但会说出来(`POST /api/scan` 回的 `appeals.missing`),`scan_appeal` 那一行留着,下次搜到自动恢复 |
| **「停更断崖」的历史有洞** | `scan_exclusion.pushed_at` 从上线起开始攒,但一个仓这一周没被 search 返回就没有行 | 那条规则将来只能写成「**有记录的那几周里连续没动过**」,不能写成「连续 N 周」的字面意思 |
| **两条端点的「最近一周」可能指向不同的周** | `GET /api/scan/changes` 不传 `weekOf` 取最近一条**跨周记录**,`GET /api/scan` 取最近一次**周扫**。有周扫没跨周记录的那一周就分叉,页面会把 A 周的结论和 B 周的清单并排摆着,**不报错** | 网页已经绕开(先读 history 定出那一周,两条都显式带 `weekOf`)。**门铃邮件将来直链 `?view=changes` 是下一个会踩的**,那条链接要带上周次;两条端点的 docblock 里都写死了这条 |
| **`week_view` 只记网页** | 风险 4 的仪器只在这两条端点上落行。只读邮件正文、没点进来的那种阅读一行都没有 | 复盘时按 docs/03「第二个月复盘」那节的边界读,别把「库里没有」读成「他没看」 |

## 四、上线之后的两个诚实判据

产品方案给这个产品定了两条「什么时候该停下来复盘」的线。它们不是上线验收，是**第二周和第二个月**的事，写在这里免得忘：

> **两条判据现在都真的查得出来了**(上线前终审之前它们都只是文档里的一句话:点击数无处可记,
> 跨周结论只存在于一封可能发不出去的邮件里)。下面各给一条能直接跑的 SQL / 一个能直接点的入口。

**风险 2 的判据**：**第二周结束时，如果点开的深度报告少于 2 份，就停下来复盘形态，不要继续加功能。**

怎么查(`<dossier_id>` 换成自己的):

```bash
wrangler d1 execute nanisle-weekly-teardown --remote --command   "SELECT COUNT(DISTINCT full_name) AS 点过几个仓, COUNT(*) AS 点了几下      FROM candidate_open WHERE scan_id LIKE '<dossier_id>#%'"
```

因为决策 4 把深度报告放在「点一行才跑」后面，整条深度线的验证权在站长的手指上。邮件来了不点，那么锚定、两节报告、永久回链——这周做的一大半——一次都没被真实使用过，**而验收会显示「功能全做完了」**。

可能的结论是清单本身已经够用（那就退回一次性扫描），也可能是邮件里放的信息不足以让人想点（那就调门铃的内容，而不是加功能）。

**风险 4 的判据**：**第二个月诚实复盘一次跨周价值。**

网站形态相对 skill 的存在理由全押在跨周状态上，而支撑它的证据只有一次（08-15 扫 12 个仓、08-21 又扫 13 个，同一领域 6 天内，n=1）。**如果站长从不去翻上一周的结果，那就该把这个产品退回 skill 形态，这不丢人。**

「翻上一周」这个动作在产品里的落点是 `GET /api/scan/changes`(上线前终审加的;在那之前
**这条判据物理上无法执行**——跨周 diff 算完只进了一封可能发不出去的邮件,库里一个字都没有,
网页上根本没有东西可翻)。每一周的结论落在 `weekly_change` 一行,查这一个月有没有变化:

```bash
wrangler d1 execute nanisle-weekly-teardown --remote --command   "SELECT week_of, prev_week_of, appeared_count, archived_count, license_count,           star_jump_count, recheck_checked, recheck_changed, recheck_unchecked, changed      FROM weekly_change ORDER BY week_of DESC LIMIT 8"
```

#### 但这条判据问的不是「有没有变化」,是「**你到底翻没翻**」

上面那句 SQL 只能证明「库里有东西可翻」。判据的原话是**「如果站长从不去翻上一周的结果」**,
主语是人不是数据。而人对自己行为的回忆偏向乐观 ——「我当然看了啊」是复盘时最容易脱口而出
的一句话,**而这条判据的全部意义就是在你不想承认时逼你承认**。所以冻结前最后一轮加了
`week_view`:每一次翻阅落一行,不上页面(实时显示的计数器会反过来改变行为),只为这一刻。

**先读懂三件事,不然会把数读错:**

1. **一次翻阅落两行。** 跨周那一屏并发打两条端点(`GET /api/scan/changes` 拿结论、
   `GET /api/scan?weekOf=` 拿那一周的清单),两条各记一行,靠 `surface` 分开。
   **数次数必须先挑一条 `surface`**,下面的 SQL 一律挑 `'changes'`;不挑就是真实次数的两倍。
2. **`explicit = 0` 是进屏时的默认加载,`= 1` 是他自己挑了一周。** 两种都记 —— 他得点那个
   入口才到得了这一屏,动作是真发生了 —— 但强度不同。
3. **`week_of < latest_week_of` 才是「翻上一周」。** `latest_week_of` 是**那一刻**库里最新的
   那一周(写行时记下来的,不是复盘时反推的)。只看最新那一周 = 「我收到了这周的清单」,
   那是一个 skill 也给得了的东西;回头去翻旧的那一份,才是这个产品存在的理由。
   `latest_week_of` 为 NULL = 那时一次周扫都还没跑过。

**① 一句话结论(判据本身)。** `<dossier_id>` 换成自己的:

```bash
wrangler d1 execute nanisle-weekly-teardown --remote --command   "SELECT COUNT(*) AS opened, SUM(explicit) AS picked,           SUM(CASE WHEN latest_week_of IS NOT NULL AND week_of < latest_week_of THEN 1 ELSE 0 END) AS looked_back,           COUNT(DISTINCT week_of) AS weeks_seen      FROM week_view WHERE dossier_id = '<dossier_id>' AND surface = 'changes'"
```

- `opened` —— 跨周那一屏一共被打开过几次;
- `picked` —— 其中几次是他**自己挑**了一周(不是默认加载);
- `looked_back` —— **判据数的就是这个数**:回头翻了一份不是最新的结果,几次;
- `weeks_seen` —— 翻到过几个不同的周。

**`looked_back` 接近 0 就是「从不去翻上一周」**,那就该按产品方案退回 skill 形态。
`opened` 不小但 `looked_back` 是 0,说的是另一件事:他会来看这一屏,但只看最新那一份
—— 那时该问的是「跨周结论要不要直接并进第一屏」,而不是继续给翻周那一列加功能。

**② 翻到过哪几周、各翻了几次:**

```bash
wrangler d1 execute nanisle-weekly-teardown --remote --command   "SELECT week_of,           CASE WHEN latest_week_of IS NULL THEN 'unknown'                WHEN week_of < latest_week_of THEN 'looked-back' ELSE 'current-only' END AS kind,           COUNT(*) AS times, MAX(at) AS last_at      FROM week_view WHERE dossier_id = '<dossier_id>' AND surface = 'changes'      GROUP BY week_of, kind ORDER BY week_of DESC"
```

同一周被翻过两次会落两行(`at` 在主键里),所以 `times > 1` 是**比「翻过」更强的信号**
——「他又回去看了一次」。

**③ 按周看行为随时间怎么变(第二个月对比第一个月):**

```bash
wrangler d1 execute nanisle-weekly-teardown --remote --command   "SELECT latest_week_of AS during_week, COUNT(*) AS opened,           SUM(CASE WHEN week_of < latest_week_of THEN 1 ELSE 0 END) AS looked_back      FROM week_view WHERE dossier_id = '<dossier_id>' AND surface = 'changes'      GROUP BY latest_week_of ORDER BY during_week DESC"
```

**注意这份数据本身的诚实边界**,复盘时别读过头:

- **它只记网页。** 门铃邮件里那些链接被点开之后照样会打到这两条端点,所以邮件那一路也算得上;
  但**只读邮件正文、根本没点进来**的那种阅读,这里一行都没有 —— 那种行为在库里不存在,
  不代表它没发生。
- **写失败不拦请求**(`store.ts` 的 `recordWeekView` 吞异常并 `console.error`)。仪器坏了不该
  让被量的行为本身发生不了,代价是这份历史可能有洞;洞会在日志里响。
- **它从上线那天开始攒。** 上线之前的两周没有任何行,不是「他没翻」,是「还没有这张表」。
