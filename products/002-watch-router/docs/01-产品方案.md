# 002 Watch Router — 产品方案(草稿)

> 状态:2026-08-22 草稿,待评审。来源:产品讨论(基于 001 的立场延伸)+ GitHub 同类项目调研(2026-08-22,引用散在正文)。
> slug 暂定 `002-watch-router`,中文名待定(见「风险与开放问题」)。

## TL;DR

做一个**长内容内部的路由器**:粘贴一个视频/播客/长文链接,AI 把能替你看的部分看掉(输出带时间戳的要点),把替不了你看的部分标出来(给出「需要你亲自看的片段」:时间范围 + 为什么 + 跳转链接),末尾附「已替你跳过」问责区。立场与 001 一致:摘要是路由器,不是终点——001 在多条内容之间路由(哪条值得点),002 在单条内容内部路由(哪几分钟值得看)。提取转写复用 kb-agent 已验证的分平台管线(字幕优先、Groq whisper 兜底),AI 编辑沿用 DeepSeek V4 Pro 接缝。第一周主打 B站长视频和播客(时间戳跳转体验完整),抖音/小红书走降级形态。

## 背景与问题

1. **视频不可扫读。** 文章可以三十秒扫完决定读不读、读哪段;一小时的视频/播客做不到,唯一的快进手段是拖进度条赌运气。这是 001 覆盖不到的内容形态:001 的「为什么值得你点」帮你决定点不点,但点进去之后的一小时仍是黑箱。
2. **通用总结已商品化,且立场有害。** 把链接丢给任何 AI 助手都能拿到摘要;B站自带 AI 总结。但 001 调研引用的实验证据([PNAS Nexus 2025](https://academic.oup.com/pnasnexus/article/4/10/pgaf316/8303888))表明读摘要比读原文知识更浅——例外是内容与读者手头的事直接相关时。002 的输入是**用户手动粘贴的链接**,天然落在例外里:用户已经决定要关心这条内容,产品要做的不是替代它,而是帮用户把有限的观看时间花在刀刃上。
3. **个人原型已存在。** kb-agent(私有仓)的 Content Inbox 流程(手机双击 → 丢链接 → EC2 提取转写 → AI 消化)就是这个产品的单用户版,已稳定运行,分平台提取手册(抖音三级降级/小红书/B站/YouTube/播客文字优先)全部实跑过。002 是把它的 Ingest 环节产品化,并把输出形态从「替你读完」改成「分流」。

## 方案

一句话:**AI 替你看完,然后诚实地告诉你哪几分钟它替不了你。**

### 决策 1:输出四段式,分流不替代

| 分区 | 内容 | 规则 |
|---|---|---|
| 判决 | 这条内容值不值得你花时间,一句话 | 结合时长与信息密度;「不值得看」是合法输出 |
| AI 替你看完的 | 要点列表,每条带时间戳 | 想核对可跳原片;只能来自转写文本,禁止外推(承袭 001 决策 3 的反捏造规则) |
| 需要你亲自看的 | 片段列表:时间范围 + 为什么替不了你 + 跳转链接 | 入选标准见决策 2;可以为空,空着就是空着,不硬凑 |
| 已替你跳过 | 跳过了多少分钟、主要是什么(寒暄/广告/车轱辘话) | 承袭 001 的问责区:省时间的价值必须可见才可信 |

### 决策 2:「需要亲自看」的入选标准——这条标准就是产品本身

只有两类片段配得上让用户亲自看:

1. **价值在画面里**:演示操作、代码屏幕、图表、实拍。转写承载不了,AI 替你看等于没看。v1 只能靠转写线索判断(「我给大家演示」「如图」「大家看这里」等话术 + 章节元数据),会有漏判,页面必须标明「基于转写判断」——这是 AI-Video-Transcriber 路径徽章的同款诚实。
2. **与你手头的事直接相关**:复用 001 的 focus/追踪器配置。同一条视频,别人拿到要点转述,你拿到「这 5 分钟在讲你正在做的东西,值得听原话」。这是 002 与所有总结工具的第二道分界,也让 002 与 001 共享同一份用户配置。

除这两类外的一切内容,消化成带时间戳的要点。

### 决策 3:按时长分形态

- **长内容(> 15 分钟,B站长视频/播客/讲座)**:完整四段式。这是主场——时间戳跳转体验完整(B站/YouTube 支持带秒数 URL 直达;播客展示时间戳供手动拖)。
- **短内容(抖音/小红书/几分钟内)**:自动降级为「判决 + 要点」两段。浅化效应对几十秒的内容不适用,深链跳转也不被平台支持,不硬套路由器。

### 决策 4:提取转写——字幕优先,转写兜底,全部继承 kb-agent

分平台路由直接抄 kb-agent 的 platform-routing 手册(抖音 iesdouyin 快速路径→Playwright→cookie 兜底;B站/YouTube yt-dlp 字幕优先;播客 transcript 标签→官网文字稿→whisper)。转写用 Groq whisper-large-v3(免费档每天 2000 请求/每小时 7200 音频秒;ffmpeg 压 32kbps 单声道约 14MB/小时,超 25MB 分段)。两处改动:

1. `response_format` 从 `json` 改 `verbose_json` 拿分段时间戳(一行改动);字幕路径的 vtt 自带时间戳。
2. 保护规则照搬:超 3 小时不转写、429 降级不阻塞。

### 决策 5:成本模型——按内容 ID 全站缓存 + 限流

BibiGPT README 明示的三板斧照单全收:同一个视频全站只提取转写一次(缓存 key = 平台 + 内容 ID,与用户无关;「亲自看」片段的 focus 相关判断是用户维度,单独算,便宜的 LLM 调用而已);每用户每日粘贴条数上限;AI 编辑用 DeepSeek V4 Pro(承袭 001 决策 10,收在同一个 AI 接缝里)。

### 决策 6:异步任务形态——Worker 收单,重活出 Worker

粘贴链接到出结果要几十秒到几分钟,不可能在 Worker 请求内完成。沿用 001「生成与展示分离」的原则:

```
网页(Worker) 收单 → 任务写 KV 队列 → 消费者(维护者 EC2,私有仓 infra 调度)
  → yt-dlp/whisper/LLM → 结果回写 KV → 页面轮询/SSE 展示进度与结果
```

进度页要像 AI-Video-Transcriber 一样把阶段亮出来(下载中/转写中/编辑中 + 走了哪条路径),等待才可忍受。消费者的具体形态(常驻最小实例轮询,还是按需拉起)在私有仓 infra 定,产品侧只依赖「队列进、结果出」;任务超时(如 10 分钟)显式报失败,不静默挂起——这是 kb-agent EC2 静默失败教训的 002 版本。

### 为什么不选(备选方案)

| 备选 | 卡点 |
|---|---|
| 通用摘要形态 | 商品化红海,BibiGPT v1 的结局;且与 001 的立场研究直接冲突 |
| v1 就上 VLM 抽关键帧判断画面价值 | BiliSum 证明可行,但一周预算装不下;v1 用转写线索 + 诚实标注,漏判感写进验收 |
| 浏览器插件/快捷指令作为第一入口 | 分发利器但不是验证期的事;先网页贴链接跑通价值假设 |
| 桌面端 + B站扫码登录 | 解 cookie 的正路,但 web 产品第一周用不上;公开内容 + 字幕路径已够验证 |
| 用 supadata 等提取 SaaS | 自建管线更强且已存在;记为自建路径被平台封死时的降级保险 |

|---|---|---|

| 2 | 提取转写脚本移植:kb-agent 路由 → 运行时无关 CLI(`npm run process -- <url>`),verbose_json 时间戳 | 2h |
| 3 | 编辑 prompt:转写 → 四段式 JSON(判决/要点/亲自看/跳过),反捏造规则同 001 | 1.5h |
| 4 | 结果页:四段式渲染 + 可点时间戳(B站/YouTube 带秒 URL)+ 路径徽章 + mock 模式内置示例 | 2h |
| 5 | 收单/队列/进度:`POST /api/submit` → KV 队列 → 轮询进度页;按内容 ID 缓存 | 1.5h |
| 6 | README + `.dev.vars.example` + 双语 catalog 行 | 0.5h |

范围收窄:v1 只接 B站 + 播客(小宇宙/RSS)+ YouTube,抖音/小红书 v2 再开(降级形态另做);消费者进程第一周可以先在维护者本机 tmux 里跑,infra 接线不阻塞验证。

### v1 验收(动手前写死)

1. **时间戳点击率**:一周内站长贴 ≥ 10 条真实长内容,「需要你亲自看」片段的跳转点击率 ≥ 50%——分流假设的直接检验:标出来的片段如果连自己都不点,说明判断标准或形态是错的。
2. **漏判感**:每条内容看完标注片段后自问「有没有错过重要内容」,10 条里出现 ≥ 2 次「漏了」,先修决策 2 的判断标准,不加功能(承袭 001 的「先修内容不加功能」)。

### v2(验证通过后)

- 抖音/小红书接入(降级两段式)
- VLM 抽关键帧:画面价值判断从转写线索升级为真看画面(BiliSum 先例)
- agent skill + MCP server(BibiGPT/BiliSum 的分发打法,约半天)
- 与 001 打通:处理完的内容可一键进入次日简报的「项目弹药」区;002 反过来成为 001 的一种信源类型(001 方案 v3 预告的 transcript sources 由此落地)
- 浏览器插件/iOS 快捷指令(「在遇到视频的地方接住链接」)

## 风险与开放问题

1. **最脆弱的假设:「分流」是不是伪需求。** 用户可能只想要结论(那通用摘要就够了,产品不成立),也可能标注的片段不可信(漏判几次后用户回到全程亲看)。验收两条各堵一头;若双双失败,退路是承认这类内容只配要点摘要,把管线并回 001 做信源。
2. **AI 看不见画面,v1 的画面价值判断是代理指标。** 转写线索的漏判率未知,验收 2 就是它的测量;v2 的 VLM 是既定升级路径,不算未知数。
3. **规模化边界(第一周不想,但要记录)。** 抖音抓取是对抗性的、cookie 兜底是单人尺度;Groq 免费额度按账号算,多用户后转付费档(whisper 约 $0.111/小时音频,可控);多租户抓取的合规性在开放注册前重新评估。
4. **转写等待体验。** 一小时播客全链路可能要几分钟,首次贴链接的用户可能等不及就走了。缓存命中的内容秒出,冷内容靠进度页留人;若流失严重,考虑「留邮箱,好了发你」(001 的邮件模块现成)。
5. **产品名。** slug 暂定 `002-watch-router`;中文名候选:替你先看 / 观看分流 / 亲自看。nanisle.com 页面文案待写。
6. **002 与 001 的关系边界。** 短期是独立小岛(独立验证、独立验收),长期是 001 的信源类型之一。合并的触发条件:002 验收通过且 001 的 v3 排期启动;在那之前两边不共享代码(conventions 的自包含规则)。
