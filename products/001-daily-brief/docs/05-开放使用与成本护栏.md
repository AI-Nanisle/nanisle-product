# 005 · 开放使用与成本护栏(白名单退役)

> 状态:已实施(2026-08-24,A/B/D 三节 + 订阅名单自动化全部上线);唯 C 节的
> 并发闸还卡在 AWS 配额批复(申请 2026-08-23 提交,10 → 1000,状态 CASE_OPENED),
> 批复后取消 `daily-brief-stack.ts` 里 `reservedConcurrentExecutions: 3` 的注释再 cdk deploy。
> 前置阅读:docs/02-技术方案.md §5.2(门禁)、§8.3(成本止损);主仓 `infra/lib/daily-brief-stack.ts`(Lambda 栈)。

## TL;DR

把「白名单准入」退役,任何注册了南屿账号的人都能直接用每日简报。DeepSeek 预充值余额是最后的总闸,但它保护的是钱包不是可用性——滥用者烧完余额,全站(包括站长自己)一起停摆。所以开放的同时上三道护栏:**注册侧限流**(better-auth 自带限流器落到 D1,magic link 发信同 IP 每分钟最多 5 次)、**AI 端点按 IP 的日额度**(防开小号绕过按账号的额度)、**恢复 Lambda 并发物理闸**(先向 AWS 申请把并发配额从 10 提上去)。另外把模型按任务分两档:选材和成稿留 `deepseek-v4-pro`,向导、改稿、口味画像蒸馏换 `deepseek-v4-flash`——交互端点更快,钱也省。

## 背景与问题

### 白名单今天干着两份工

1. **准入门禁**:`src/worker/guard.ts:96`,每个带个人数据的请求都查一次 `store.isWhitelisted(email)`,不在名单里的登录用户拿到 403「产品内测中」。
2. **定时刊的订阅名单**:每天 07:00 的全量生成(`pipeline/lambda.ts:426` 的 `generateAll`)就是遍历 `listWhitelist()` 来决定给谁生成。

所以「关掉白名单」不是删一行判断:门禁放开后,还得回答「定时刊给谁生成」——否则新用户配好了追踪器,第二天早上却没有刊。

### 为什么不能裸开

主站注册是开放的 magic link(`web/lib/auth.ts`,Resend 发信),任何人可以无限注册账号。现有防线在这个前提下的实际效力:

| 防线 | 现状 | 开放后的漏洞 |
|---|---|---|
| 每日额度:立即生成 10 次、编辑调用 60 次(`src/shared/store.ts:101`) | 有效 | 按账号计,开 N 个小号就有 N 倍额度;没有按 IP 的限制 |
| Lambda 并发物理闸(`reservedConcurrentExecutions: 3`) | **从未生效**——账号总并发配额只有 10(新账号最低档,2026-08-23 实查确认),AWS 要求预留后剩余 ≥ 10,任何预留值都被 CloudFormation 拒绝,2026-08-21 已注释停用 | 无硬上限,只剩应用层的「一人同时一趟」 |
| 调用量告警(60 次/小时,`infra/lib/daily-brief-stack.ts:252`) | 有效 | 只发邮件不拦截,看到告警前成本照跑 |
| Resend 登录邮件 | 有效 | 免费档有日发送量上限,被刷注册会把真实用户的登录一起堵死 |
| DeepSeek 预充值余额 | 有效 | 硬上限,但烧完后所有人的简报一起失败——它是保险丝,不是限流器 |

结论:开放前必须补「按 IP 限流」和「物理并发闸」这两块;模型分档不是安全需求,是趁着改配置顺手把交互延迟和单位成本降下来。

## 方案

### A · 白名单退役,订阅名单自动化

**门禁**:删掉 `guard.ts:96` 的白名单判断,`userGuard` 只要求有效会话。403「内测中」文案与前端对应的拦截态一并移除。`adminGuard`(站长访问码)不动。

**定时刊扇出**:`generateAll` 不再遍历「站长手工维护的名单」,改为遍历「配置过追踪器的用户」。实现上不新建表:沿用 DynamoDB 里现有的名单条目(`WL#` 键),但语义从「站长准入名单」变成「订阅名单」——用户第一次保存配置(`putConfig`)时自动把自己写进去。这样 `generateAll` 一行不用改,`listWhitelist()` 读到的就是所有配置过的用户。

为什么不改成「扫全表找 CONFIG 条目」:DynamoDB 单表按主键设计,没有「列出所有用户的 CONFIG」的高效查询,要么加 GSI(全局二级索引,给表加一份按另一个键排序的副本)要么 Scan 全表。沿用现有名单集合零迁移、零新索引,`putConfig` 加一次幂等写入即可(幂等 = 重复执行结果相同,写十次和写一次一样)。

配套改动:
- `store-kv.ts`(本地 dev / fork 的替身存储)同样在 `putConfig` 里自动入名单。
- `infra/scripts/whitelist-add.ps1` 退役,README 里的白名单运维段落删掉。
- `generateAll` 里名单成员没有 CONFIG 时本来就跳过(`lambda.ts:429` 起),行为不变。

**没做的事(有意的)**:不活跃用户暂停。开放后每个配置过的用户都会**永久**占一份每日成本(一次选材 + 一次成稿的模型调用 + Lambda 运行时间),试一天就走的人也一样。这次评审明确不做,见「风险与开放问题」。

### B · 限流:两层,各管一头

#### B1 · 注册/登录侧(主站,better-auth 自带限流器)

better-auth 内置速率限制,magic-link 插件甚至自带了规则(该路径 60 秒 / 5 次,按 IP 计),**但默认存储是进程内存**——Workers 每个 isolate 一份内存,限流计数互相看不见,等于没限。修复方式是把存储切到数据库:better-auth 支持 `rateLimit.storage: "database"`,计数落到 AUTH_DB(D1)里一张 `rateLimit` 表。

`web/lib/auth.ts` 增加:

```ts
rateLimit: {
  enabled: true,          // 默认只在 NODE_ENV=production 开;显式写死,行为不随构建环境漂
  storage: "database",
},
advanced: {
  ipAddress: { ipAddressHeaders: ["cf-connecting-ip"] },  // Cloudflare 边缘注入的真实客户端 IP
},
```

配套一条 D1 migration 建 `rateLimit` 表(字段 `key` / `count` / `lastRequest`,见 better-auth 文档的 rate-limit schema),走现有 `wrangler d1 migrations apply nanisle-auth` 流程。

生效后的实际限额:magic link 发信同 IP 每分钟 5 次(插件默认规则),所有 auth 路径同 IP 每分钟 100 次(全局默认)。刷注册从「无限」变成「每 IP 每小时最多 300 封发信请求」,而 Resend 免费档余量之内真实用户不受影响。

**为什么不用 Cloudflare 零售的 WAF 限流规则**:zone 级规则配置在 dashboard 里,不进 git、不进评审,和「配置即代码」的现状相悖;而且免费档只有 1 条规则,留给紧急止血用更值。better-auth 方案全部落在仓库里,`npm run deploy` 一次生效。

#### B2 · AI 端点侧(产品 Worker,按 IP 的日额度)

按账号的日额度(gen 10 / ai 60)保留不动,**再加一层按 IP 的日额度**:同一 IP 当天所有账号合计,立即生成 20 次、编辑调用 120 次(账号上限的 2 倍——家庭/办公室共用出口 IP 的两个真人不受影响,但一个人开 10 个小号会在第 2 个小号处撞墙)。

实现完全复用现有额度机制:`store-dynamo.ts` 的 `reserveQuota` / `refundQuota` 已经是「按 (主体, 日期, 类型) 原子计数 + 超限拒绝 + DynamoDB 原生 TTL 七天过期」,把主体从 email 泛化成「email 或 `ip#<地址>`」即可,不加新表不加新依赖。调用点在 `userAiGuard` 通过后、按账号额度检查的同一处,IP 从 `cf-connecting-ip` 头取(产品 Worker 经主站 Service Binding 转调,原始请求头原样传递,该头由 Cloudflare 边缘写入、用户伪造不了)。

两层配合后的滥用账本:单 IP 每天最多烧 20 次生成 + 120 次编辑调用;想扩大就得换 IP,而分布式滥用(肯到处找 IP 池来刷一个中文简报产品)的动机与收益不成比例——真到那一步,还有 C 的并发闸把烧钱速率封顶,DeepSeek 余额是最后的保险丝。

**为什么不用 Workers 的 ratelimit binding**(Cloudflare 的原生限流绑定):它只支持 10 秒 / 60 秒窗口,做不了「每天」这个粒度;而我们要防的是「一天内开小号刷额度」,短窗口限不住慢刷。复用 DynamoDB 计数还让 KV 替身模式(fork / 本地)行为一致。

### C · Lambda 并发物理闸恢复

栈里那行 `reservedConcurrentExecutions: 3` 的意图没变(同时最多 3 条生成管线,多余调用被 Lambda 平台直接 429,不依赖任何应用代码),卡点只是账号配额。分两步:

1. **现在就提申请**(不依赖代码,批复要等几天):

   ```powershell
   aws service-quotas request-service-quota-increase `
     --service-code lambda --quota-code L-B99A9384 `
     --desired-value 1000 --profile kb-agent --region us-east-1
   ```

   要 1000(AWS 的标准默认档)而不是最低需求 13:配额申请是人工/半自动审批,要小数字和要标准档的通过难度差不多,一次到位免得以后再等。批复少于 1000 也无妨,≥ 13 就够用(预留 3 之后剩余 ≥ 10)。

2. **批复后**:取消 `daily-brief-stack.ts:92` 的注释,`cdk deploy`(profile kb-agent)。验证:`aws lambda get-function-concurrency --function-name nanisle-daily-brief-generate` 应返回 3。

闸值仍取 3:定时刊是单次调用内部串行,立即生成受 GENRUN 闸(一人同时一趟)约束,正常并发到不了 3;这个值封顶的是「所有应用层防线全失效」时的烧钱速率——每条管线数分钟量级,3 条并发意味着每小时最多几十次模型调用,告警(60 次/小时)有充足时间响。

### D · 模型分档:重任务 pro,轻任务 flash

现状:全链路默认 `deepseek-v4-pro`(带 thinking,深思考但慢、贵),只有成稿有独立换模开关(`ENRICH_AI_*`)。产品里的 AI 调用点逐一过一遍:

| 调用点 | 位置 | 任务性质 | 建议档位 | 理由 |
|---|---|---|---|---|
| 选材(编辑判断) | `pipeline/lambda.ts:163`、Worker 内联 `index.ts:1128` | 从上百条候选里按追踪定义挑选、归簇 | **pro** | 候选池大、判断链长,thinking 直接影响选材质量,是产品的核心口碑 |
| 成稿(enrich) | `pipeline/lambda.ts:302`、`index.ts:1154` | 读者读到的散文全在这段 | **pro**(保留 `ENRICH_AI_*` 开关) | 文字质量敏感;后台任务,慢一点无所谓 |
| 口味画像蒸馏 | `pipeline/lambda.ts:256`、`index.ts:1103` | 把点击/反馈流水摘要成画像 | **flash** | 结构化摘要任务,不需要深思考 |
| 向导 understand / tags / sources | `src/worker/wizard.ts:243,336,490` | 交互式:理解诉求、出标签、提议信源 | **flash** | 用户在等页面转圈,pro 的 thinking 延迟直接伤体验;任务本身模板化程度高 |
| 对编辑说一句(refine) | `/api/refine` → wizard.ts | 按用户一句话改追踪定义 | **flash** | 同上 |

实现沿用成稿开关的既有模式,新增「轻任务档」配置:

- `shared/ai.ts` 侧不动(`complete()` 本来就吃 `AiConfig`)。
- Lambda:`envFastAiConfig(base)` 读 `FAST_AI_PROVIDER` / `FAST_AI_MODEL`,默认——当基础 provider 是 deepseek 时取 `deepseek-v4-flash`,否则跟随基础配置(anthropic / gateway / mock 模式下不强塞 deepseek 型号,零配置和换模对照的规矩不破)。口味画像蒸馏改用它。
- Worker:`env.ts` 的 `AppEnv` 加同名变量,`aiConfig(env)` 加一个 `fastAiConfig(env)` 变体;`runWizard`(`index.ts:838`)和 refine、蒸馏改用它。
- 主仓栈:Lambda environment 注入 `FAST_AI_MODEL`(默认 `deepseek-v4-flash`,可被部署时环境变量覆盖);产品 Worker 的 `wrangler.jsonc` vars 加 `"FAST_AI_MODEL": "deepseek-v4-flash"`。

**一处要盯的质量回归**:向导找源(`wizard/sources`)是五个 flash 调用点里最吃「见识」的——要按追踪定义提议真实存在、能抓通的 feed。它有 `probeFeed` 存活探测和自动重调兜底(抓不通会带失败清单再问一次),所以坏提议不会直接进配置,但如果 flash 的提议存活率明显变低,重调次数上升、向导变慢,应把 sources 单独切回 pro(实现上给 wizard 分调用点传配置即可,方案先不做这层细分,等实测数据)。

## 风险与开放问题

1. **不活跃用户的长期成本(本次明确不做,但要立观察哨)**。每个配置过的用户 = 每天一次 pro 选材 + 一次 pro 成稿,永久持续。订阅名单到 30 人量级时(约为当前调用量告警阈值能兜住的上限),应回头补「N 天未登录暂停生成、下次访问自动恢复」。触发信号:告警邮件频率、DeepSeek 余额消耗斜率。
2. **SES 还在沙箱**:邮件推送只能发给已验证地址,新用户配置完拿不到早间邮件,只能回网页看。这不是本方案引入的,但开放注册会放大它的体感——AWS 批复前,配置页/成功态文案里别承诺邮件。
3. **按 IP 限流防不了分布式滥用**。判断是:这个产品的滥用收益(白嫖一个中文简报生成器)撑不起 IP 池的成本,且并发闸 + DeepSeek 余额兜底。若判断错了,零成本的下一步是把 Cloudflare zone 那条免费 WAF 规则用上(紧急止血),再考虑注册加人机验证。
4. **flash 在向导找源上的质量未实测**,见 D 节末段;上线后第一周抽查 sources 的存活率与重调率。
5. **最脆弱的假设**:「同 IP 多账号 = 滥用」。公司/校园大出口 NAT 下,20 次/日的 IP 上限可能误伤真实多用户。内测阶段用户量小,风险可接受;误伤发生时把 IP 上限调高是一行配置改动,且按账号额度仍在,不会放大成本风险。
